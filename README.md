# xmip-core-transport

Direction-neutral Transport contracts for moving immutable Streams between Xmip and endpoints.

Receive and Send own orchestration, ports, groups, and locations. Transport owns byte movement and resource claims; it does not own authentication, message representation, contract evaluation, or operation semantics.

This crate is the common boundary: the `Transport` trait, `Arrived`, `Directions`, the error vocabulary (which takes the network primitives' failures with `From`, and becomes `xcore::Failure` with `From` — retryable as it was — so a technology whose attempt the resilience guards judge writes `?`), and resource claims. It holds what the SQL technologies share (`sql.rs`): where a send target puts its row, the one INSERT with its table and column quoted as the technology's `Dialect` says, the same statement taken apart for a far end, the declared payload column, and what a receive does with the rows its query read (`sql::accept`): each row an arrival, and the `accept` statement that consumes it after an accepting cycle — a refused row is left and not handed on again while its body is unchanged — the row's name bound as a literal in place of the dialect's first parameter; each technology passes its dialect, and nothing tells one from another by name; the target is read by `net::Target` against the schemes the dialect declares. It holds `Configured` (`configured.rs`), the companion every technology implements to declare its settings — each one's name, kind, default or requirement, meaning and side, in the shape `xmip-core` owns (`xcore::settings`, the one a contract's settings take too) — and to be built from a Location's address and settings read through that one declaration, so what `configure` refuses at start, what the language server and the desktop editor offer, and what the technology reads cannot disagree (ADR-0064, amendment 2026-09-26). `Configured::on_node` is how the runtime gives a transport its node, once, as it builds it — the node's location, `NodeLocation` (`node.rs`), never a node argument on each technology's constructor (the owner's *Option A*, 2026-10-03): a technology that records at the far end who holds what — the file transport's claimed names (ADR-0024, amendment 2026-09-26) — keeps it, and returns there what the node held before it last stopped; by default it keeps nothing. It holds the loopback rig every technology's far end is built from (ADR-0051): the `Loopback` trait and its round — which goes in order on one thread where a technology declares `exchanges_in_order`, and releases a far end whose near end failed by poking a TCP listener, never a datagram far end (`FarEnd::datagram`) — and its `arrival_identity`, which every round holds the far end's arrival to — the names, from `xmip-core-context`, under which a technology writes what it observed of the sender on every `Arrived` (the socket peer, a hardware address), or why it has nothing beyond the origin (`ArrivalIdentity`, ADR-0019 amendment 2026-10-06), and whether the arrival was pushed, detected or scheduled — the far ends `Listening` (TCP), `Bound` (UDP) and `Held` (in process), the `Standing` sessions of an in-process pair, `both_ends` and `poke`; a technology keeps only what its far end does with the exchange. The byte cursor and writer, hex, the CRCs and the varint are encoding primitives, and each technology takes them from `xmip-core-library-codec` itself, as it takes X.690 from `xmip-core-library-asn1` and the one refusal of a payload over a protocol's ceiling from `xmip-core-library-net` (`net::ceiling::within`). Its test support (`test-support`, from a technology's dev-dependencies only) carries the edge and sized payloads a loopback round is exercised with, and `latency`: a round's median, p99 and worst, and a plain loopback TCP wake measured beside it, so a technology holds its latency to a bound *apart from load* (the owner, 2026-09-26). Nothing in it names a protocol. Each transport technology is its own repository (ADR-0010) mounted directly under this one and depends on this crate, never the reverse; `architecture.toml` names them and carries each one's maturity, and this file does not repeat the list.

**A receive consumes nothing; the far end is acknowledged after the receive cycle** (the owner, 2026-10-01; runtime-model section 5). `Arrived` (`arrived.rs`) carries where a Stream came from, its body as a reader (`std::io::Read + Send`) the runtime pulls in chunks into the Ledger — never a whole buffer where the far end can stream; a protocol that hands over a whole message gives a reader over it (`Arrived::whole`) — and its `Acknowledgement` (`acknowledgement.rs`). The runtime gives that one `Verdict` once the cycle has ended: `Accepted`, and the far end consumes (the file moved or deleted, the queue message deleted or committed, the protocol's positive answer sent); `Refused`, with why (`Refusal`: unidentified, forbidden, unacceptable), and it hears the protocol's permanent rejection — a `4xx`, an error MDN, an HL7 `AE`, a reject without requeue — and does not send the Stream again; a refusal is not a consumption, so where Xmip polled the Stream from a far end that holds the only copy, a file in a drop directory, it is set aside — moved to the technology's refused place where it has one, otherwise left where it lies and not received again while it stays as it was refused — because a refusal at a transport gate kept nothing in Xmip; `Failed`, where Xmip could not complete the cycle (Xmip Storage did not take it, its body broke), and it keeps the Stream and sends it again, or hears the protocol's transient answer (`503`, an HL7 `AR`, a busy code). A log read from a place (`contiguous.rs`) moves past an accepted or refused record and holds at a failed one. Every technology declares whether its arrivals are ordered (`arrivals.rs`, `Transport::arrivals`, no default, its reason in words): where the far end's position matters — a contiguous cursor, a queue settled in order, a directory or table polled again — every arrival of one receive gets its verdict, in order, before the next receive; where each connection, request or datagram is its own, or a lease or lock keeps what is in its cycle from being handed out twice, the technology is asked again at once and the runtime carries its arrivals side by side, up to the Receive Location's pool. Nothing acknowledges by default: a technology builds its acknowledgement `deferred`, with what its protocol does for each verdict, or `at_most_once`, with the reason in words, where the protocol took the Stream from its sender as it arrived — a datagram, a push already answered — and its README says so. One dropped without a verdict consumes nothing. Until 2026-10-02 `Arrived` was the origin and the whole body, and most technologies consumed as they received — a file deleted, a queue message deleted, `202` sent — before anything was durable. What a far end takes in a loopback round is a `Taken` (`taken.rs`): the origin and the bytes, whole, already answered; a far end built on its technology's own receive takes each arrival with `Arrived::taken`.

**A send carries its deduplication key** (built 2026-10-04; runtime-model section 15, *Delivery semantics*). The runtime sends through `Transport::send_keyed`, with the Journey's identifier as the key: the same on every attempt of one Journey, different for every other, so a Message routed twice to one endpoint is two deliveries and a retry of one Journey is the same one. A technology whose protocol carries an identifier its far end deduplicates by puts the key there and its README says where; every other keeps the default, which ignores the key and sends as `send` does — at least once, never silently at most once.

What several technologies' acknowledgements share lives here once, and each calls it. A read that consumes nothing at the far end — a register polled, a variable read, a `SELECT` that deletes nothing — is acknowledged `Acknowledgement::unconsumed`: neither verdict has anything to tell, and a cycle that did not complete loses nothing, so it is not at-most-once. A body the far end streams is read as the runtime asks (`body.rs`): `body::opened` opens it by its first read (a dropped file, an FTP transfer), `body::fetched` fetches a whole message then (an IMAP or POP3 message, a WebDAV `GET`), and `body::chunked` pulls it a chunk at a time until its source says the end (an NFS, SMB or SFTP read). A log read on from a place — a Kafka or Redpanda partition, a Redis Stream, a Kinesis shard — keeps that place in a `contiguous::Contiguous`, which a verdict moves only from where it stands: accepting the record after `k` moves it to that record only where it stands at `k`, and a refused record and every one read after it are read again. A receive from an object store — an S3 bucket, an Azure Blob container, a Google Cloud Storage bucket — is `listed::listed`: it lists, each object's `GET` is made when the runtime first reads its body, and its acknowledgement deletes it on `Accepted` only, leaves it on `Failed`, and on `Refused` leaves it and remembers its `ETag`. An XML listing's objects are read by one scan, `listed::Listing` — the element each object is and the elements holding its name and its stamp — which S3 and Azure Blob each name. What a Location refused and left where it lies is remembered once, in `refused::Refused` (`refused.rs`): each item by its name with its stamp — a length and a modification time, an `ETag`, a hash of a row's body — and a listing leaves out every item that still lies as it was refused, asking the stamp only of a refused name, so a protocol whose listing names files without stamps (FTP's `NLST`) asks the far end for the few it needs; one written again under its name is a new arrival, and a refusal whose item is gone or changed is forgotten. The memory is the node process's: a node that starts again receives a refused item once more. The file transport, the object stores, the SQL technologies and the remote file and mail technologies all call it. Arrivals settled together after the last verdict — POP3's `QUIT`, IMAP's `EXPUNGE`, an MQ unit of work, a SQL claim — are `together::together`. A delivery's answer goes on the session it came on or not at all (`Pool::kept`: an AMQP `basic.ack`, a STOMP ACK, an MQTT `PUBACK`, a JetStream `+ACK`, an MQ commit); where that session is gone, nothing is opened and the far end delivers again. A request–response protocol's answer waits for the verdict on its connection (`answer.rs`): `answer::Answer` holds the connection — a clone, so the kept connection reads on — writes the answer once, marks the connection `answer::Busy` until then where the protocol answers one request at a time (`serving::Open::busy`: HTTP, SMTP), and shuts it when let go unanswered, so the peer is never left waiting and sends again; `answer::Datagram` sends a datagram's answer from a clone of the socket it came on (CoAP, DNS, SNMP, BACnet, KNXnet/IP).

Its sockets (`socket.rs`, `sender.rs`) are opened once and waited on rather than polled wherever the operating system lets a safe call wait. `socket::accept_within` is the one bounded accept, for any `socket::Acceptor` — a TCP listener, a Unix domain socket's, a named pipe's: it waits on the listener's readiness, poll(2) or `WSAPoll` through `rustix`'s safe `event::poll`, and takes a connection as it lands, `accept_tcp` handing it back with Nagle's algorithm off as `net::connect` does; until 2026-09-27 the capability, the named pipe and the Unix domain socket each polled with a two-millisecond nap, and a Windows named pipe, which has no readiness a safe call can wait on, still naps a quarter of a millisecond between tries. `socket::connect_tcp` is `net::connect`, every address a name resolves to inside one deadline; it tried only the first until 2026-09-27. A send target and an origin are read by `net::Target`, in `xmip-core-library-net`, which every technology calls itself: `socket::target` split one on its first slash, the query left in the path, until 2026-09-28. `sender::Sender` is the datagram socket a UDP technology sends from, bound once per address family — IPv6 targets included — and kept by the transport and its clones, with `exchange` holding it for a request and its answer after reading off whatever came late; nine technologies bound a new IPv4 socket for every datagram until 2026-09-27.

A Receive Location's listener is bound once and kept (`kept.rs`): `kept::Kept` holds whatever the technology binds — a TCP listener, a datagram socket, a Unix domain socket's listener, a named pipe — bound by the technology's own `bind` on the first receive and taken from by every receive after, so what connects or arrives between two receives waits in the operating system's backlog or buffer and the next receive takes it. Thirty technologies bound a new listener in every `receive`, took one exchange and dropped it until 2026-09-27, so a peer that connected between receives was refused and a datagram sent then was lost. `serving::Serving` is a kept listener and the connections its peers keep open on it (at most `MOST_KEPT`): one readiness wait over all of them hands each receive the next exchange from whichever peer speaks first, a new one accepted and kept or a kept one's next — what one exchange on a connection is stays the technology's (the http technology's `inbound`). `kept::held_across_receives` (test support) holds a technology to it: payloads sent to the kept address while it receives, every one taken in order by receives that bind nothing.

A Send Location's sessions are opened and logged in once and kept (`pool.rs`): `pool::Pool` holds, per address, the sessions a transport and its clones send on — an HTTP connection, an MQTT or NATS client, an AMQP channel in confirm mode, a SQL login, an SMB tree, an SSH connection — each taken for one exchange and put back after, so sends on several threads each have one. A session says through `pool::Pooled::usable` whether it can carry another exchange, and `pool::alive` is the check one over TCP makes: a peek that sees a far end that hung up without waiting on it. Before a pool opens a session it lets go every kept one that is no longer usable, under every address, so a session whose far end hung up is closed by the next one opened rather than kept under an address never asked for again — until 2026-09-29 the Playground's nodes kept one such socket a round, in `CLOSE_WAIT`, until the machine ran out of ephemeral ports; `pool::quiet` is the stricter check for a session whose far end speaks only when asked. One that fails on reuse is dropped and the exchange goes again on a new one, so a send is carried at least once, and a send that is not idempotent can be carried twice where the first attempt reached the far end and only its answer was lost. The http technology's `endpoint::Connections` is this pool's instance for HTTP; twenty technologies connected, logged in and closed for every message until 2026-09-27. A Receive Location that connects out — a broker consumer, a SQL poll, a mailbox, a file share, a plant read — keeps its session in the same pool from 2026-09-28: logged in on its first receive, reused by every receive after, replaced when the far end closed it; a subscription or consumer stays attached between receives, and `pool::delivered` drains one until it is quiet, telling a quiet subscription (kept) from a broken one (replaced). POP3 alone connects per receive, because its session fixes the maildrop at login and commits deletes at QUIT. `login::Login` is the user and password a technology logs in with, printed without its password; eight technologies and MQTT declared the pair each until the same day. Where a protocol frames a Stream by the connection itself — raw TCP and a Unix domain socket, closed to end it; COTP class 0, whose receiver takes a caller's messages until it disconnects and which acknowledges none; a WebSocket, whose receiver takes one frame a connection with nothing said back — the send connects per message, because a kept connection could not tell a Stream that landed from one written into a closing socket.
